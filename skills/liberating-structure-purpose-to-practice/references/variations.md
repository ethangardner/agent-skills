# Variations

Read this when the user asks for one of these modes, or when a plain forward
run isn't the right shape for what they brought.

## Pressure-test persona: the Future Participant

Optional, and not part of the core structure — a single invented voice you
can bring in after Principles and Structure are drafted, to stress-test them
before the user commits.

The persona is a **future participant**: someone who will actually live
inside this initiative once it launches, not a stakeholder in the design
room. They read the draft Principles and Structure and react the way a real
person subject to them would — skeptically, and specifically. Their signature
question, asked of each principle in turn: *"Does this actually constrain
how I'd behave, or is it just a nice thing to have written down?"* Of the
Structure: *"When I disagree with a decision, whose call is it, actually —
and how would I find that out before it happens to me?"*

Use this only as an add-on when the user wants their draft pressure-tested
harder than the standard check-against-Purpose step already does, or when
Phase 2/4 keep producing answers that feel safe rather than sharp. It is not
a core phase — don't invent this persona automatically on every run, and
don't let it turn into a full second consultation. One or two pointed
reactions per element is enough; the point is friction, not a new structure
layered on top of this one.

## Retrofit: auditing an initiative that skipped this

Some initiatives never went through anything like P2P — they accreted a
purpose after the fact, if they have one written down at all. Use this mode
when the user describes something already running (a team, a project, a
program) that's struggling, drifting, or losing people, and you suspect the
root cause is that it never had a real Purpose to check anything against.

Run the same five elements, same strict order, but reframed as an audit
rather than a design session:

1. **Purpose** — ask what they'd currently say the purpose is, then apply the
   same pressure as Phase 1 of the core structure. Very often what surfaces
   here is that the stated purpose is actually a Practice ("our purpose is to
   ship the weekly report") or a platitude with no discriminating power. Name
   that plainly if it's what you find — it's usually the actual diagnosis for
   why the initiative feels adrift.
2. **Principles** — ask what rules the group actually follows, in practice,
   not what's written in a doc somewhere. Compare the lived rules to the
   Purpose that just got surfaced or reconstructed. Mismatches here (rules
   that serve a different, unstated purpose) are diagnostic.
3. **Participants** — ask who's actually at the table today versus who the
   real Purpose would require. This is often where the drift shows up
   starkest: initiatives accrete convenient participants over time and lose
   the ones the purpose actually needed.
4. **Structure** — ask how decisions actually get made today, not how the org
   chart says they get made. Check against Purpose the same way.
5. **Practices** — the one thing that's usually already well-documented.
   Check every current practice against the reconstructed Purpose and
   Principles; practices that fail the check are candidates to cut, not just
   observations.

The output of a retrofit run isn't a fresh chart to launch — it's a diagnosis
of where the existing initiative's chart and its lived reality have diverged,
plus a short list of the highest-leverage places to realign. Say so
explicitly at the start, so the user doesn't expect this to feel like
building something new. If the audit turns up that there was genuinely never
a real Purpose, that's often the finding itself, and worth stating as
directly as that: this struggled because it was never actually anchored to
one, not because of anything on the Practices layer.
